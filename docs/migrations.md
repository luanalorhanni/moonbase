# Migrations workflow

> **Project rule:** the agent (Claude Code) prepares migration scripts but **never executes them against the database**. A human operator (you) runs each migration, after reviewing the SQL and confirming the connection string targets the intended environment.

## Pre-requisites

- `.env.local` populated with a `DATABASE_URL` pointing at a **direct connection** (Supabase host `db.<ref>.supabase.co`, port `5432`).
  - The transaction pooler (port `6543`, host `aws-...pooler.supabase.com`) does **not** support the DDL transactions drizzle-kit emits and will fail.
- Postgres role with privileges to run `CREATE TABLE`, `CREATE TYPE`, and `ALTER TABLE … ENABLE ROW LEVEL SECURITY`. The default `postgres` user on a fresh Supabase project has these.

## Files involved

```
lib/db/
├── schema.ts               # canonical TypeScript schema (source of truth)
├── index.ts                # Drizzle client used at runtime
└── migrations/
    ├── 0000_*.sql          # generated by drizzle-kit from schema.ts
    ├── 0001_enable_rls.sql # hand-written; RLS is not generated by drizzle-kit
    └── meta/
        ├── _journal.json   # registry of applied migration tags (ordered)
        └── 0000_*.json     # snapshot of the schema at that revision
```

## Day-to-day commands

| Command            | What it does                                                          | Touches DB?    |
| ------------------ | --------------------------------------------------------------------- | -------------- |
| `pnpm db:generate` | Diffs `schema.ts` against the latest meta snapshot, writes a new SQL file | No             |
| `pnpm db:migrate`  | Applies pending migrations in order, records them in `__drizzle_migrations` | **Yes — DDL** |
| `pnpm db:studio`   | Local database browser at `https://local.drizzle.studio`              | Read-only UI   |
| `pnpm db:push`     | Skips migrations and pushes the schema directly                       | **Yes — destructive** |

## Workflow for a normal schema change

1. Edit `lib/db/schema.ts`.
2. Run `pnpm db:generate` — produces a new `lib/db/migrations/<n>_<name>.sql` file.
3. **Open the SQL file and review it.** Drizzle is good but not infallible — confirm the diff matches the change you intended (especially `ALTER` and `DROP` statements).
4. Commit `schema.ts`, the new SQL file, and the updated `meta/` snapshot in the same PR.
5. After the PR is merged: run `pnpm db:migrate` from your laptop with `.env.local` pointing at the production direct connection. Drizzle records the migration in `__drizzle_migrations`, so re-running is a no-op.

## Workflow for changes drizzle-kit cannot generate (RLS, triggers, raw SQL)

1. Run `pnpm db:generate --custom --name=<descriptive_name>` — creates an empty SQL migration file registered in the journal.
2. Fill the file in by hand.
3. Same review/commit/apply cycle as above.

## First-run checklist

The first deploy applies two migrations in order:

1. `0000_<random>.sql` — creates 7 enums and 13 tables with foreign keys.
2. `0001_enable_rls.sql` — enables RLS on every table and applies four canonical policies (select/insert/update/delete) scoped by `auth.uid() = user_id`.

After running `pnpm db:migrate`, confirm the result:

```bash
pnpm db:studio
```

Open the browser link drizzle-studio prints. Expect:

- 13 tables under the `public` schema (`cards`, `categories`, `subcategories`, `cards`, `card_closings`, `credit_expenses`, `cash_expenses`, `fixed_expenses`, `incomes`, `cash_receivables`, `credit_receivables`, `liquid_savings`, `fixed_income`, `monthly_snapshots`).
- 7 enum types (`card_type`, `cash_method`, `payment_method`, `income_type`, `loan_type`, `snapshot_status`, `color`).

For RLS verification, drizzle-studio does not display policies. Either:

- Inspect the **Authentication → Policies** tab in the Supabase dashboard, or
- Run in the SQL editor:
  ```sql
  SELECT schemaname, tablename, policyname, cmd
  FROM pg_policies
  WHERE schemaname = 'public'
  ORDER BY tablename, cmd;
  ```
  Expect 4 policies × 13 tables = **52 rows**.

## Things to avoid

- **Never** edit a migration SQL file after it has been applied to any environment. Write a new migration instead.
- **Never** run `pnpm db:push` against the production Supabase project. It bypasses the migration history and is fine for ephemeral local dev only.
- **Never** edit production schema directly in the Supabase dashboard. The dashboard's table editor will not be reflected in `schema.ts`, and the next `pnpm db:generate` will try to "correct" the drift in confusing ways.
